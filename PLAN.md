# План развития ScratchJr Web

Дата создания: 2026-08-04
Репозиторий: `AndreiPabiarzhyn/ScratchJr-Desktop`

## Цель

Переделать проект из Electron desktop-приложения в статический сайт без бэкенда:
вся логика ScratchJr работает в браузере, данные пользователя хранятся полностью
в браузере (IndexedDB), деплой — статический хостинг (например, GitHub Pages).
Решение принято 2026-08-04 взамен предыдущей десктоп-траектории (см. «Архив:
десктоп-этапы» ниже) — не в дополнение к ней.

## Правила работы

- После каждого заметного изменения обновлять этот файл.
- Не смешивать механическую гигиену, исправления поведения и портирование на веб
  в одном коммите.
- Перед изменениями в хранилище данных (IndexedDB/sql.js) делать резервную копию
  сценария и проверять восстановление.
- Для каждого завершённого милстоуна фиксировать критерий приёмки и его
  результат.
- Независимые проверки/аудиты выполнять параллельными субагентами (инструмент
  `Agent`), мутирующие и рискованные действия — только основным агентом после
  явного согласия пользователя.

## Архитектурное решение

- **Хранилище**: `sql.js` (обновить до современного WASM-билда `sql.js@1.x`)
  выполняется прямо в браузере; вся SQL-логика `src/app/src/iPad/IO.js`
  остаётся без изменений. Бинарный экспорт БД (`db.export()`) персистится в
  IndexedDB одним ключом (например, через `idb-keyval`). Медиафайлы (SVG/аудио/
  картинки) как и раньше хранятся внутри той же SQLite БД в таблице
  `PROJECTFILES` — отдельная IndexedDB-схема для медиа не нужна.
- **Единственный шов замены** — `src/app/src/iPad/iOS.js` (`tabletInterface`)
  сегодня указывает на `window.tablet = new ElectronDesktopInterface()`
  (`src/electronClient.js`). Порт — это в основном написание
  `WebTabletInterface` с тем же набором методов + добавление сборщика, а не
  переписывание `src/app/src/**` (редактор/рисовалка/лобби уже не зависят от
  Electron напрямую).
- **Сборка**: Vite в режиме multi-page app (4 входа: `index.html`, `home.html`,
  `editor.html`, `gettingstarted.html`) — сохраняет текущую модель обычной
  многостраничной навигации (`window.location.href = '...'`), без переписывания
  на SPA-роутер.
- **Экспорт/импорт `.sqlite`** — добавляется как резервная копия/перенос между
  устройствами (решение пользователя, т.к. без файловой системы IndexedDB —
  единственное хранилище).
- **Один активный набор проектов** — без поддержки нескольких БД-«наборов»
  (starter kits) на первом этапе (решение пользователя).
- **`analyticsEvent` убирается**, **parental gate остаётся** как есть (решение
  пользователя).

По пути найдены и исправлены 4 реальные ошибки инициализации в браузере (все
не имели отношения к БД напрямую, но блокировали запуск любой страницы):
- `global is not defined` — `vite.config.js`: добавлен `define: {global:
  'globalThis'}` (старые Node-ориентированные зависимости — jszip, sql.js,
  intl — ссылаются на Node-глобал `global`).
- `eve is not defined` — `snapsvg`'s `dist/snap.svg.js` присваивает
  необъявленной глобальной `eve` (работало в Electron только благодаря
  нестрогому CJS-враппер Node). Фикс: `globalThis.eve = undefined;` в самом
  начале `webClient.js` (первый импорт `appEntry.js`) — переприсваивание
  существующей глобали strict mode разрешает, в отличие от объявления новой.
- `require is not defined` — `src/app/src/utils/Localization.js` использовал
  рантайм `require(...)` (старый Babel/electron-compile паттерн) для загрузки
  locale-data файлов `intl`/`intl-messageformat`. Заменено на статические
  `import '...'`.
- `IntlMessageFormat is not defined` — после замены `require` на `import`,
  `intl-messageformat/dist/locale-data/*` (которым нужен уже готовый глобал
  `IntlMessageFormat`) стали грузиться ДО присвоения `global.IntlMessageFormat
  = ...` (ES-импорты хоистятся и резолвятся в порядке следования, в отличие
  от `require()`, который выполнялся строго по порядку строк). Исправлено
  вынесением в отдельный модуль `utils/intlMessageFormatGlobal.js`,
  импортируемый первым, до locale-data импортов.
- Дополнительно: `Uncaught InvalidCharacterError` в `btoa` — сид-проект
  ссылался на миниатюру как `"samples/Bump.png"` (путь для галереи сэмплов),
  а код «Моих проектов» (`Home.js`→`IO.getAsset`) ждёт обычный MD5-ключ из
  `PROJECTFILES`; поправлено в `webDb.js` (префикс `samples/` убран из сида).
- `src/app/css/` перенесён в `src/app/public/css/` — эти файлы на самом деле
  шаблоны с `${...}` JS-выражениями (вычисляются рантайм-препроцессором
  приложения, не настоящий CSS), а Vite пытался парсить их через PostCSS при
  любом прямом запросе `.css`, даже вне графа модулей. `publicDir` отдаёт их
  как есть, без какой-либо обработки.

## Пост-деплой: найден и исправлен баг продакшен-сборки

После деплоя на GitHub Pages пользователь сообщил, что `index.html` не
загружается — застревает на сплэш-логотипе. Консоль показала:
`Uncaught ReferenceError: css_vw is not defined`, внутри `preprocess()`
(`utils/lib.js`), которая делает `eval()` над текстом, вырезанным из CSS
(`${css_vw(21.68)}` — шаблонные выражения внутри `.css`-файлов, вычисляемые
приложением само по себе, не браузером).

**Причина**: всё предыдущее тестирование (M1-M7) шло через `npm run dev`
(без минификации) — там `css_vw`/`css_vh`/`scaleMultiplier` сохраняли свои
имена. `npm run build` минифицирует код, и минификатор переименовывает
локальные переменные/функции, которые, по его данным, никто не использует
статически — а обращение к ним есть только внутри строки, которую потом
`eval()`-ит `preprocess()`, что минификатор не может проанализировать.
Итог: на dev-сервере всё работало, на реальном продакшен-билде (и,
соответственно, на GitHub Pages) — ломалось. Это показало реальный пробел в
процессе проверки: `npm run preview` (реальная минифицированная сборка) не
запускался ни разу за все M1-M7, хотя `npm run build` запускался регулярно
(сборка «без ошибок» ≠ «работает в браузере»).

**Исправление**: в `utils/lib.js` после объявления `css_vh`/`css_vw`
добавлено явное `globalThis.css_vh = css_vh; globalThis.css_vw = css_vw;
globalThis.scaleMultiplier = scaleMultiplier;` — тот же приём, что уже
использовался для `eve`/`IntlMessageFormat` в M2: имена свойств объекта
минификатор не трогает (только имена переменных/функций), а поиск голого
идентификатора в `eval()`-коде падает через scope chain до глобального
объекта. Все 3 идентификатора, вызываемые таким образом из CSS, найдены
через `grep -rEo '\$\{[a-zA-Z_][a-zA-Z0-9_]*' src/app/public/css/` —
`css_vh`, `css_vw`, `scaleMultiplier` (и встроенный `Math`, который в
переименовании не нуждается).

**Дополнительная проверка после фикса**: `npm run build` → `npm run preview`
(не `dev`!) → все 4 страницы (`index`, `home`, `editor?pmd5=1&mode=edit`,
`gettingstarted` через общий бандл) открыты в чистом профиле с временным
`window.onerror`-диагностикой в заголовке вкладки — ни одной ошибки. Только
после этого пересобрано, закоммичено и передеплоено.

**Урок на будущее** (для следующих правок): после любого изменения в коде,
который читается через `eval`/`Function`/динамические строки, проверять
именно `npm run preview`, а не только `npm run dev` — минификация — это
отдельная стадия, которая может сломать то, что работало в dev-режиме.

## Пост-деплой: перетаскиваемый блок не виден пока тащишь из палитры

Пользователь: тащишь блок из палитры в код — не видно, как он идёт за
мышкой, появляется только когда отпускаешь кнопку. Внутри área кода (блок за
блок) — тащится нормально, видно сразу. Это код, который я не трогал ни на
одном из шагов M1-M7 (`utils/Events.js`, `editor/blocks/Block.js`) — похоже
на баг, унаследованный из оригинального приложения, а не регрессию.

**Причина**: `Events.move3D` (вызывается на каждый `mousemove` во время
любого перетаскивания блока) каждый раз ЗАНОВО вычисляет текущую позицию
элемента через `new WebKitCSSMatrix(window.getComputedStyle(el).webkitTransform)`,
а не хранит её. Для блока, который тащишь ВТОРОЙ раз (уже существующий в
DOM, отрисованный давно) — это надёжно работает. Но для блока, только что
СОЗДАННОГО перетаскиванием из палитры (`Palette.prepareForDrag` →
`duplicateBlock` — новый `<div>`, которому transform ставится в тот же
синхронный тик), браузер может не успеть отразить только что установленный
`transform` в `getComputedStyle()` к моменту немедленного обратного чтения —
получаем матрицу тождества (0,0), и `move3D` откладывает позицию от 0,0
вместо реальной точки создания клона, унося "призрак" куда-то не туда на
весь остаток перетаскивания. Отпускание мыши срабатывает ДРУГОЙ код (снап
блока на место), который не зависит от этого — поэтому блок «появляется»
только в конце.

**Исправление**: `move3D` (`utils/Events.js`) больше не читает
`getComputedStyle`/`WebKitCSSMatrix` — вместо этого использует кэшированные
`el.top`/`el.left` (те же кастомные JS-свойства, которые `Block.moveBlock`
и сам `move3D` и так поддерживают в согласованном состоянии), плюс
дополнительно пишет стандартный `transform` рядом с `webkitTransform` (на
будущее, если браузеры когда-нибудь перестанут алиасить префиксное
свойство). Точечная правка одной функции, остальные использования
`WebKitCSSMatrix` в кодовой базе (все — на уже стабильных, давно
отрисованных элементах) не тронуты — они не подвержены этой гонке по
построению.

**Не проверено вручную** (нужна реальная последовательность
mousedown→mousemove→mouseup с реальными правами доступа мыши — не то, что
безопасно автоматизировать на живом рабочем столе пользователя): сам жест
перетаскивания. Логика перепроверена по коду построчно, страница грузится
без ошибок после правки — но финальное подтверждение нужно от пользователя
руками.
